# Context-window ablation — findings

**Batteries:** `bench_runs/20260730_040404` (baseline) plus the seven
`*_context-ablation-*` batteries run by `configs/context-ablation/run_all.sh` on
2026-07-30.
**Scope:** 6 prompts × 3 tries = 18 attempts per arm, 144 attempts and 330 legs
across the eight arms.
**Model:** Qwen/Qwen3.6-27B for every role, every arm.
**Scoring:** success rate over 3 tries per prompt. An attempt counts only if a
human reviewer passed it on replay. Denominators are always 18; nothing is
excluded.
**Reproduce:** `analysis/context-ablation/run_all.sh` rebuilds every table and
every quoted excerpt below into `results.txt`, from `bench_runs/` alone.

> **Sample size.** Three tries per prompt. Every success confidence interval below
> is 37–42 points wide and **no arm differs significantly from baseline** (best
> *p* = 0.505). This battery can detect a policy that breaks the agent outright;
> it cannot rank two policies. Treat the success numbers as a screen. The cost
> numbers are far better powered — they come from 330 legs, not 18 attempts.

### A1 — drop the semantic append log

**Change:** `SemanticLog.render()` returns the base map dump only.
**Seam:** `overhaul/agent_core/context.py:42-48` — `semantic_keep_last=0`.

```python
def render(self) -> str:
    keep_last = self._policy.semantic_keep_last
    entries = self._entries if keep_last is None else self._entries[-keep_last:]
    # ``[-0:]`` means all entries in Python, while A1 intentionally means none.
    if keep_last == 0:
        entries = []
    return self._base_text + self._format(entries)
```

**Before** — `20260730_040404/medium_01/try01/semantic_memory.txt`, 18,913 bytes,
8 appended entries the learner re-read on every step:

```

Checkpoint 35, which is adjacent to the biscuit aisle (Checkpoint 32). To reach the
checkout from the shelves, navigate via Checkpoint 35.
@ leg 2 step 2: The self-checkout station at Checkpoint 64 features a terminal with a
'Start' button and a barcode scanner. To scan an item, the agent must be in
manipulation mode and position the held item over the scanner.
```

**After** — `…-a1/medium_01/try01/semantic_memory.txt`, 17,162 bytes, 0 appended
entries. The store ends at the last line of the base map dump:

```

  rotation: (0.0, 241.9, 0.0)
```

Every A1 run ends at exactly 17,162 bytes — min, median and max identical. That
is the invariant check that the seam fired.

### A2c — dedupe on append, render the last 12

**Change:** reject an entry whose `difflib.SequenceMatcher` ratio exceeds 0.80
against any of the last 8 survivors; render the last 12.
**Seam:** `overhaul/agent_core/context.py:30-48`.

```python
def append(self, tag: str, text: str) -> bool:
    threshold = self._policy.semantic_dedupe
    if threshold is not None:
        recent = self._entries[-self._policy.semantic_dedupe_window :]

            difflib.SequenceMatcher(None, text, existing).ratio() > threshold
            for _existing_tag, existing in recent
```

## Cost: where the context actually goes

Per-run totals are **not** a cost measurement. An attempt that runs to the
40-minute leg cap spends 40 minutes of tokens, so `tok_in/attempt` mostly measures
how long an arm survived (baseline 1.0M, a1 2.4M, a5 2.3M). None of those
differences are significant.

### The growth model

The actor's history is rebuilt at each leg boundary, so growth has to be fitted
*within* a leg. If the k-th call of a leg is handed `base + slope·(k−1)` input
tokens, a leg of n calls spends `base·n + slope·n(n−1)/2`. Fitting that through
the origin over each arm's legs (n ≥ 3 calls, `growth.py`) recovers both terms
without per-call token counts, which the harness does not record. R² ≥ 0.99
throughout.

## A4 does not do what it is named for

**The 600-char cap fired zero times.** Measured over every findings summary the
battery emitted (`findings.py`):

| arm | summaries | median chars | max chars | **exactly 600 (truncated)** |
|-----|-----------|--------------|-----------|------------------------------|
| baseline | 27 | 3,654 | 4,293 | 0/27 |
| a3 | **0** | — | — | — |
| a4 | 18 | **588** | **598** | **0/18** |
| every other arm | 18–35 | ~3,600 | 4,185–5,142 | 0 |

The rewritten prompt lands at a median of 588 characters on its own; the maximum
observed is 598, two below the cap. A4 measured a **prompt rewrite**; the
truncation it is named for is dead code in this data.

That is a better result than the arm was designed for: asking for a concise
handoff instead of a comprehensive one cut findings by **84%** (3,686 → 565 mean
chars) with no measurable task cost (10/18 vs baseline 11/18, *p* = 1.000). Length
was a property of the prompt, not of the task.

Two consequences: re-run A4 as two arms (prompt rewrite alone, cap alone) or the
result cannot be attributed; and if the cap is kept, truncate on a sentence
boundary — a hard `[:600]` slice mid-token is a latent format hazard even though
it never triggered here.

## Two harness problems found while checking the data

### 1. The auto predicate over-grants at 18%

17 of 94 auto-passes were overturned on review, one auto-fail promoted. It is
one-directional and large enough to reverse this report's headline. A battery
compared without grading is not interpretable.

### 2. A false positive destroys the prompt's remaining attempts

When the predicate grants, the operator stops that prompt's remaining tries as
`already_successful` and the harness kills them. If the grant is later overturned,
those tries are gone. It happened twice (`censoring.py`):

| arm | prompt | winning try | auto | review | cost |
|-----|--------|-------------|------|--------|------|
| a3 | hard_01 | `hard_01/try01` | pass | **fail** | 2 attempts destroyed |
| a4 | hard_03 | `hard_03/try01` | pass | **fail** | 2 attempts destroyed |

Both arms are now recorded as never solving that prompt, on the strength of one
bad grant. Fix: don't let an ungraded auto-grant trigger the sibling kill, or
re-queue the prompt when a winner is overturned.

track of where it has been, and A5 (episodic removed) and A6-4 (visual history
capped) both showing it is consistent with the actor losing its own history. But
a6-2 cuts *more* visual history and shows only ×3 — so the story is not "less
history, more wandering", and this needs a targeted look rather than a conclusion.

**If one thing ships: A6-2.** It is the only arm nominally above baseline on
success *and* cutting the dominant growth term — 43% per actor call at call 40 —

above baseline. The success edge is not significant, but "cuts cost 43% at the
tail and does not hurt" is the strongest claim this battery can support, and A6-2
is the only arm that supports it.

**A2c ships alongside** as cheap worst-case insurance, on the understanding that
the semantic log is a small term.

**The A4 prompt rewrite is the most interesting result in the battery**, and it is
not what the battery set out to test.

## What to change for the next run

1. **Grade every arm, including the control, before comparing anything.** The
   ungraded baseline reversed this report's conclusion once.
2. **Don't let an ungraded auto-grant kill siblings.** Four attempts were lost.
3. **Fix the prompt set.** Drop `easy_03` and `medium_03` (no signal). Keep
   `hard_03` and `hard_01` (the only discriminating prompts). Spend the freed
   budget on tries: 10 tries × 4 prompts beats 3 × 6 at the same compute.
4. **Split A4** into prompt-rewrite and cap-only arms.
5. **Add a long-leg prompt.** A6's payoff is entirely in the tail and the median
   leg here is 4–7 actor calls. Nothing in this battery exercises the regime the
   A6 arms were built for.
6. **Record per-call token counts.** Every growth number here is a model fit
   because the harness stores per-leg aggregates only. One field per LLM call
   makes the central measurement a direct observation.
7. **Fit A6 with a saturating curve**, not a linear one.
